# Frozen MATLAB heart-fit benchmark dependencies

This directory contains unmodified public release archives and their original extracted bytes.
`provenance.json` records version, archive revision, URL, download time, SHA-256 of every file,
and archive SHA-256. `method_mapping.json` binds registry М1–М9 (ASCII API IDs M1–M9)
to exact functions. All three packages carry their original BSD two-clause licenses.
No historical RFBR implementation identity or physiological validation is established.
Project methods Г/Л and library methods М remain separate even when values coincide.

| API IDs | Package | Release | Archive revision |

## Invocation and reproducibility

From the repository root (Python needs NumPy and SciPy):

```text
python MATLAB_TRKG4_real_subjects/tools/heart_library_fits.py self-test
python MATLAB_TRKG4_real_subjects/tools/heart_library_fits.py prepare --synthetic --shared-mat --output <new-output-dir>
python MATLAB_TRKG4_real_subjects/tools/heart_library_fits.py prepare --input <batch.json-or-mat> --shared-mat --output <new-output-dir>
```

For weighted inputs explicitly append either `--weight-policy equal_vertices` or
`--weight-policy deterministic_weight_resample --sample-count 20000`.
The first explicitly ignores supplied weights and preserves original vertex weighting.
The second uses deterministic cumulative midpoint resampling of the supplied point weights.
It approximates that discrete weighted measure, not a continuous triangle surface sampler.
Point ordering and sample count matter. Check convergence before interpreting small differences.
There is no hidden weighting change inside any upstream function.

Prepare creates `input.json`, `source_snapshot.json`, optionally `shared_points.mat`, and an
exact command in `RUN_AFTER_COORDINATOR_APPROVAL.txt`. The preparer never launches MATLAB.
Use the command only in coordination with running FEM work. The MATLAB runner enforces
`maxNumCompThreads(1)`, starts no pool, performs no FEM, and processes every cloud and all
nine methods within one MATLAB process. Each prepared cloud is reused for all methods.

```matlab
addpath('MATLAB_TRKG4_real_subjects/src');
run_heart_library_fits('<new-output-dir>/input.json', '<new-output-dir>/results.json');
```

```text
python MATLAB_TRKG4_real_subjects/tools/heart_library_fits.py audit --input <new-output-dir>/input.json --results <new-output-dir>/results.json --output <new-output-dir>/audit.json
```

Output directories/results are not overwritten. Large arrays and medical source data must
remain local and excluded from commits. This standalone exploratory benchmark does not
change `run_pipeline.m`, notebooks or their canonical result contracts.

## Stable public input contract

JSON: `{"units":"mm","cases":[{"id":"case_01","points_mm":[[1,2,3],...],
"weights":[...],"source_metadata":{"target":"whole_heart"}}]}`.
Each cloud is finite Nx3 physical mm, N>=10, spatial rank 3. `weights` and `source_metadata`
are optional. Coordinates have no implicit axis conversion. Carry the real coordinate system,
mask/source hashes, target phase and segmentation interpretation in `source_metadata`.
No anatomical correctness is inferred from those labels. Automatic target-phase mask and
transformed individual form must have different case IDs and explicit origins.

MAT source: global string `units='mm'`, with either a struct array `cases` using the same
fields or a single `points_mm` Nx3 variable plus optional `id`, `weights`, `source_metadata`.
The Python preparer reads MATLAB v5/v7 MAT through scipy.io; v7.3 HDF5 is not supported.
A batch uses one global weighting policy and one fit configuration. Split experiments into
separate prepared batches when these factors differ.

Prepared JSON has schema `heart_library_fits_input_v1`, `units`, `cases`, `methods`,
`settings`, original file SHA and vendor manifest SHA. Inline mode uses `cases[].points_mm`.
Shared-MAT mode stores each cloud once as `points_00001`, `points_00002`, etc.; JSON refers
through `cases[].points_mat_variable`, `shared_points_mat` and `shared_points_mat_sha256`.
This MAT is generated by the preparer and must stay beside its JSON. Metadata preserves
sampling policy, original/fit point counts, source and fit array hashes (C-order little-endian
float64) and resampling indices. Source file hash also binds the original weights.

## Stable output contract

Schema `heart_library_fits_output_v1`; `fits` has one row per case x M1–M9, including failures.
Fields: `case_id`, `method_id`, `method_name`, `valid`, `status`, `upstream_success`,
`centre_mm` (1x3), `axes_mm` (three SEMIaxes, descending), `orientation_columns` (3x3),
`radius_mm` (only M7/M9), `shape_tensor_mm2`, `volume_mm3`, `settings`, `sampling`,
`upstream_parameters`, `upstream_auxiliary`, `console_text`, warning/error fields and time.
`x = centre + orientation_columns * principal_coordinates` defines orientation.
For repeated eigenvalues the orientation is not identifiable; compare the shape tensor.
`shape_tensor_mm2 = R * diag(axes_mm.^2) * R'` removes eigenvector sign ambiguity.
`implicit_unit_quadric_rms` is dimensionless and NOT an orthogonal surface-distance error.
Empty arrays mark unavailable fields. JSON null may represent a nonfinite upstream diagnostic
on failure; such a row has `valid=false`. Never treat a failure as a zero geometric error.
Root fields bind exact input, vendor and adapter hashes and MATLAB version. `valid_geometry`
only means finite real positive radii, orthogonal frame and relevant quadric checks passed.

## Source audit: API limitations and explicit choices

* M1–M6: all THREE positional arguments are always supplied as `(data, regularization,
  method)`. The upstream defaults test `nargin` against the wrong variable; calling with two
  arguments can read an undefined `method`. One help example reverses method and lambda.
  No upstream patch was made. All name/value pairs are explicit, even in number, and drawn
  from the supported subset. `eta` is passed only to HES. Unpaired trailing options would
  be silently ignored upstream and are not exposed by this adapter.
* Baseline lambda is explicitly 0 (unregularized), not the package default eps and not auto.
  `--regularization` allows a finite nonnegative fixed value; `--eta` allows finite eta>=1.
  Auto, negative lambda, infinite eta, forceOrigin and forceAxial are not exposed in this
  first benchmark. Normalization is the package's own mean translation and single scalar
  global coordinate range/2. There is no external centering/scaling of M7–M9.
* Upstream warns about TAUB regularization even when explicit lambda=0; the warning is
  retained with the actual returned lambda. It does not imply regularization was applied.
* `hyperellipsoidfit` returns implicit coefficients and algebraic residuals in normalized
  coordinates; these are not distances in mm. Its mapping uses SVD and discards eigenvalue
  signs, so the adapter additionally reconstructs and checks the signed normalized quadric
  for positive definiteness and consistency of centre and mapping. No output is repaired.
* M7/M8 archive has filename `ellipsoid_fit.m` but first-line function `ellipsoid_fit_new`.
  Runtime makes a byte-identical filename alias `ellipsoid_fit_new.m` under the output
  directory, checks its SHA and records the rename. Body and upstream bytes are unchanged.
  Explicit flags are `'xyz'` for M7 and `''` for M8; legacy numeric examples are not used.
* M8 is algebraic normal-equation fitting with a quadratic-trace constraint, not geometric
  closest-point least squares. Source comments claim trace +3, while the constructed
  coefficient vector has trace -3 (an overall equation sign convention). Signed radii can
  represent a hyperboloid; nonpositive radii are rejected. Its `chi2` implementation sums
  absolute unit-quadric residuals, despite a comment calling this a sum of squares.
* M9 explicitly minimizes sum((distance-to-centre squared - radius squared)^2), an algebraic
  sphere objective. It uses moment/normal equations and assumes nonsingular coordinates.
  M7 and M9 remain separate registry entries; agreement does not merge provenance.
* All libraries use unweighted input points. No actual archive demonstrated here is proven
  to be the version or invocation used in RFBR. Only names M1–M6 occur in the report.

## Completed synthetic evidence

`output/exploratory/heart_library_fits_20260915/synthetic_01/` contains two exact known
surfaces, 600 points each, translated sphere and rotated ellipsoid, prepared shared MAT,
MATLAB R2025b output and independent geometric audit. All 18 fits returned valid geometry.
All 16 exact-recovery checks passed (9 sphere fits, 7 ellipsoid-capable fits). M7/M9 on
ellipsoid are approximation controls, not exact-recovery claims. Max centre error was
1.99e-13 mm and max relative shape-tensor error 2.74e-14. Tolerances: centre <1e-5 mm,
relative tensor <1e-6. Single computational thread; no FEM/pool. The first invocation
stopped before fits on a relative-path assertion; canonical path handling was fixed and
both startup logs retained. Python checks cover source hashes, synthetic surface truth,
weighting determinism, invalid-weight and coplanar rejection, and MAT/JSON ingestion.

This establishes adapter operation on ideal inputs. It does not establish noisy-surface
accuracy, robustness to outliers, segmentation accuracy, resampling convergence, electrical
adequacy, physiological validity or superiority among methods. HES restrictions and
regularization may matter for elongated or irregular hearts and require separate cases.
